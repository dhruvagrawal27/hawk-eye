## Deviations / assumptions
- **pandas-3.0 compatibility convention (cross-laptop — see CONTEXT.md 2026-06-30 [DATA] note).** pandas 3.0 makes string columns the extension `StringDtype`, so `np.issubdtype(series.dtype, np.number)` raises `TypeError`. **ALL ML code uses `pd.api.types.is_numeric_dtype(series)` (and the `pd.api.types.*` family) — never `np.issubdtype` on a Series dtype.** The `.mlvenv` currently resolves pandas to 2.3.3 (a downstream lib pins `<3`), but ML code is written to run on **both** 2.3.x and 3.0.x so it stays portable across the DATA venv (3.0.3) and the ML venv. Verified: DATA suite = 100/100 on pandas 3.0.3 after the fix.
- Heavy deps are import-guarded via `ml/_optional.py` (HAS_* flags, now **lazy** via PEP-562 `__getattr__` so `import ml` does NOT eagerly load torch+lightgbm together) so every module imports and core paths run even if an optional lib is missing; deep models (torch/PyG) are REAL because the stack installs cleanly.
- **macOS dual-OpenMP constraint (cross-laptop — also in CONTEXT.md for PLATFORM CI).** torch ships its own `libomp` and so do LightGBM/sklearn; co-loading both into one long-lived process **segfaults** mid-run (a platform threading hazard, not a test failure). Resolution: **run each test file in its own process.** The canonical entry point is **`.mlvenv/bin/python -m ml.tests.run`** (per-file subprocess runner → 100/100 green). A single-process `pytest tests/ml/` will crash once both torch and LightGBM get used; per-file isolation avoids it. `KMP_DUPLICATE_LIB_OK=TRUE` is set in `ml/_optional.py`; conftest deliberately does NOT import torch (that would load it into LightGBM-only processes).
